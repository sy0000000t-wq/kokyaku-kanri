# 電気保安管理 顧客管理ツール

電気管理技術者（個人事業）向けの、保安管理契約物件を一元管理するローカル Web アプリです。
顧客マスタ・点検スケジュール・請求／入金を1つの SQLite ファイルで管理します。

仕様は [電気保安管理_顧客管理ツール_仕様書.md](電気保安管理_顧客管理ツール_仕様書.md) を参照してください。

## 公開先

**https://sy0000000t-wq.github.io/kokyaku-kanri/**

スマホからも PC からも、このURLで使えます（モバイル回線でも可）。
データは利用者自身の Google ドライブの `顧客管理データ.json` に保存され、
このサイト自体はデータを持ちません。

`main` に push すると GitHub Actions が「テスト → ビルド → 公開」を自動で行います。

## セットアップ

Finder で **`start-mac.command` をダブルクリック**すると、必要な準備をしてから
サーバーを起動し、ブラウザを開きます。停止はそのウィンドウで Control + C。

ターミナルから動かす場合:

```bash
npm install
npm run db:migrate    # SQLite スキーマ作成 + 初期マスタ投入
npm run dev           # http://localhost:3100
```

ポートは **3100** です（3000 は別プロジェクトが使っているため）。

`npm run db:migrate` は何度実行しても安全です（スキーマは差分適用、マスタは未登録のものだけ追加）。

タグ `v0.1-周期一律倍率` 時点の DB がある場合、`npm run db:migrate` が旧スキーマを自動で検出し、
中身を `data/backup/pre-flowchart-*.json` に退避してから新スキーマへ移行します。
顧客・点検実績・請求実績・設定はそのまま引き継がれます。

本番起動:

```bash
npm run build && npm run start
```

### 検証用サンプルデータ

```bash
npm run db:seed:sample
```

`data/sample-customers.json` を読み込みます。このファイルは**実在の顧客情報を含むため `.gitignore` 済み**で、
リポジトリには入りません。ファイルが無い場合はダミーの `data/sample-customers.example.json` が使われます。

## スマートフォンからのアクセス

開発サーバーは `next dev -H 0.0.0.0` で起動するため、同一 LAN 内の端末から見られます。

**Mac の名前（Bonjour）で開くのがおすすめです。** IP アドレスは Wi-Fi ルーターの都合で
勝手に変わることがあり、そのたびに URL が切れてしまうためです。名前なら変わりません。

```bash
# Mac の名前を確認する
scutil --get LocalHostName
```

スマートフォンのブラウザで `http://<表示された名前>.local:3100` を開き、ブックマークします。

繋がらないときの予備として IP でも開けます。

```bash
ipconfig getifaddr en0
```

`start-mac.command` から起動した場合は、両方の URL が起動時に表示されます。

同じネットワーク（同じ Wi-Fi）に繋がっていること、Mac のファイアウォールが Node の着信を
許可していることが条件です。現場では点検スケジュール画面の「当月の点検リスト」が主用途で、
連絡先はタップで発信、住所はタップで Google マップが開きます。

## データとバックアップ

| 場所 | 内容 |
|---|---|
| `data/app.db` | データベース本体。これ1つで全データが完結します |
| `data/backup/app-YYYYMMDD.db` | 起動時の自動バックアップ。同日分は上書き、30日で自動削除 |
| `data/deleted/*.json` | 顧客を完全削除したときの退避データ |

いずれも `.gitignore` 済みです。

### 復元手順

1. アプリを停止する（`npm run dev` / `npm run start` を Ctrl+C）
2. 戻したい日付のバックアップを本体に上書きコピーする

```bash
cp data/backup/app-20260823.db data/app.db
```

3. `data/app.db-wal` と `data/app.db-shm` が残っていれば削除する
4. アプリを起動し直す

設定 → データ管理から取得した **JSON 一括エクスポート**からも復元できます。
インポートは現在のデータを全置換するため、実行前に必ずエクスポートを取ってください。

## 保安管理点数の考え方

出典は **換算値算出フロー図（2025-01-09）**。倍率は点検周期だけでは決まらず、
**設備区分と点検周期の組み合わせ**で決まります。区分によっては係数表を使わず固定点数です。

| 設備区分 | 点数の決まり方 |
|---|---|
| 需要設備（低圧） | 月1回 0.3 ／ 2ヶ月 0.18（固定） |
| 高圧 64kVA未満・小規模高圧設備 | 3ヶ月 **0.2 固定**（絶縁監視装置 必須） |
| 高圧 64kVA未満・非常用予備発電設備あり | 月1回 0.4 ／ 2ヶ月 0.24（固定） |
| 高圧 64kVA以上100kVA以下 | 月1回 0.6 ／ 2ヶ月 0.36 ／ 3ヶ月 0.27（固定） |
| 高圧 100kVA超過 | 係数表 × 月1回 1.0 ／ 2ヶ月 0.6 |
| EV専用充電設備（1000kVA未満） | 月1回 0.40 ／ 2ヶ月 0.24（固定） |
| 火力発電所（ディーゼル・ガスタービン等） | 係数表 × 月1回 1.0 ／ 3ヶ月 0.45 |
| 太陽電池発電所（自家消費） | 係数表 × 6ヶ月 0.25 |
| 太陽電池発電所（全量売電） | 係数表 × 2ヶ月 0.36 ／ 3ヶ月 0.33 ／ 4ヶ月 0.32 ／ 6ヶ月 0.31 |
| 蓄電所 | 係数表 × 月1回 1.0 |
| 配電線路のみ | 0.1 固定 |

### 併設の事業場は設備ごとに出して合算する

1つの事業場に設備が複数あり、それぞれ別の周期を持つことがあります。
点数は**設備ごとに算出して合計**します（フロー図の参考例そのままです）。

```
参考例1  需要設備 300kVA  2ヶ月点検   0.8 × 0.6  = 0.48
         太陽光（自家消費）80kW 6ヶ月点検 0.3 × 0.25 = 0.075
                                              計 0.555 点

参考例2  需要設備 550kVA  2ヶ月点検   1.2 × 0.6  = 0.72
         ディーゼル(発) 80kW 毎月点検              = 0.3
         太陽電池(発) 100kW 全量売電 3ヶ月 0.4 × 0.33 = 0.132
                                              計 1.152 点
```

この2例は `npm test` の検証ケースに入れてあります。

顧客編集画面では「設備を追加」で行を増やし、設備ごとに区分・容量・周期を選びます。
画面右の計算プレビューに設備ごとの内訳と合計が出ます。

### 換算係数を手で決める

係数表を使う区分では、換算係数の指定方法を3つから選べます。

| 指定方法 | 用途 |
|---|---|
| 容量から自動判定 | 既定。容量が属するレンジの係数を使う |
| **係数表から選ぶ** | レンジ一覧から係数を直接選ぶ。容量の届出値と実態が違うときなど |
| 数値を直接入力 | 表にない係数を使うとき |

手動で決めた場合は一覧・プレビューに「手動」バッジが付きます。
固定点数の区分（低圧・64kVA未満・EV充電設備など）は容量によらないため、手動指定は効きません。

## マスタの更新手順

換算係数・設備区分・周期ごとの倍率・請求サイクルは、すべて DB から読み込んでいます。
アプリのコードに固定値は書かれていないので、**設定画面から変更すれば全画面に反映されます**。

### 設備区分と倍率

1. 設定 → 設備区分タブを開く
2. 左の一覧から区分を選ぶ（「＋ 区分を追加」で新規作成）
3. 「点数の決め方」で係数表方式か固定方式かを決める
4. 下の「〜 の点検周期」で、その区分で選べる周期と倍率（または固定点数）を編集する
   - 「絶縁監視装置が必須」「注記（条件適用 など）」は入力画面にバッジで出ます
   - 設備に使われている周期は削除できません

### 換算係数テーブル

1. 設定 → 換算係数タブを開く
2. 右上のセレクタで編集するテーブル（需要設備 / 太陽光・蓄電所）を選ぶ
3. 行を編集・追加・削除する
   - 下限は「以上」、上限は「未満」
   - 上限を**空欄**にすると「上限なし」になります（最上位行に1つだけ置けます）
4. レンジの重複・欠落はその場で検証され、エラーがあると保存できません
5. 「このテーブルを保存」を押す

太陽光・蓄電所テーブルには告示に定めのある 5000kW 未満までしか行がありません。
5000kW 以上の物件を登録する場合はここに行を追加してください。

### 訪問周期

設定 → 訪問周期タブは**現場に行く周期**のマスタです。点検月のプリセットに使うだけで、
点数計算には影響しません（点数側の周期は設備区分タブで設定します）。

## 距離の算出について

| モード | 使うもの | 精度 |
|---|---|---|
| 道路距離 | Google Geocoding API + Routes API | 番地レベル。所要時間も出ます |
| 直線距離 | OpenStreetMap Nominatim + Haversine | **町・大字レベル** |

設定の距離算出モードが「自動」のとき、API キーがあれば道路距離、無ければ直線距離になります。

距離は**顧客の保存時と「再計算」ボタンを押したときだけ**算出し、結果は DB にキャッシュします。
一覧を開くたびに API を叩くことはありません。

### 直線距離モードの制約

Nominatim は日本の番地・小字をほとんど収録していません。そのため住所を
「全体 → 番地を落とす → 町/村まで → 市/区/郡まで」の順に丸めながら再試行します。
つまり**得られる座標は町・大字の代表点**で、実際の物件から 1〜2km ずれることがあります。

また Nominatim は自由文検索であいまい一致するため、放っておくと別の市の施設が返ることがあります
（実際に「愛知県豊田市仮町仮田」で豊橋市の保育園が返る例がありました）。
そのため都道府県と市区郡が一致しない結果は破棄しています。

正確な距離が必要な物件は、顧客編集画面の「緯度・経度を手入力する」から座標を直接入れてください。
手入力した座標は住所を変えても保持されます（住所だけを変えた場合はキャッシュを捨てて取り直します）。

Nominatim の利用規約に従い、リクエストは 1 秒に 1 回までに制限しています。
一括再計算に時間がかかるのはこのためです。`.env.local` の `NOMINATIM_USER_AGENT` に
連絡先を含む User-Agent を設定してください。

## API キーの扱い

Google Maps API キーは次の順で解決されます。

1. `.env.local` の `GOOGLE_MAPS_API_KEY`（**推奨**）
2. 設定画面で保存した値

**設定画面から保存したキーは SQLite に平文で入ります。** `data/app.db` を人に渡したり
クラウドに置いたりする場合は注意してください。`.env.local` は `.gitignore` 済みです。

```bash
cp .env.local.example .env.local
# エディタで GOOGLE_MAPS_API_KEY を記入
```

## 契約解除と削除

物件を対象から外す方法は2段階あります。**通常は「稼働停止」を使ってください。**

| 操作 | 効果 |
|---|---|
| 稼働トグルを OFF（解除日を入力） | 解除日以降のスケジュール・請求対象から外れる。実績・チェックはすべて残る |
| 顧客編集画面の「削除」（二段階確認） | 顧客と関連実績を削除。削除前に `data/deleted/` へ JSON を自動退避 |

各画面の既定フィルタは「稼働中のみ」です。「すべて」に切り替えると解除済みの行が淡色＋
「解除（日付）」バッジで表示されます。集計値は表示中の行ではなく、常に稼働中の行が対象です。

## 開発

```bash
npm test          # 計算ロジックのユニットテスト
npm run test:watch
npm run build     # 型チェック込みの本番ビルド
```

計算ロジックは `lib/calc/` に純関数として置き、UI からは計算式を持ち込まない方針です。

| ファイル | 内容 |
|---|---|
| `lib/calc/coefficient.ts` | 換算係数・設備ごとの点数・事業場の合計（換算値算出フロー図） |
| `lib/calc/pricing.ts` | 月額・年額・点数単価（§4.2） |
| `lib/calc/schedule.ts` | 実施月の生成、稼働判定、点検対象の導出（§4.4） |
| `lib/calc/billing.ts` | 請求月・請求額・入金予定・未入金判定（§4.5） |
| `lib/calc/coefficient-range.ts` | 換算係数テーブルのレンジ検証（§5.7） |
| `lib/geo/` | 距離算出。`GoogleProvider` / `HaversineProvider` を差し替え可能 |

検証ケースは `npm test` で確認できます。

- 換算値算出フロー図の全分岐（低圧・64kVA未満・64〜100kVA・100kVA超過・EV充電設備・
  火力・太陽光の自家消費／全量売電・配電線路のみ）
- フロー図の参考例1（0.555 点）・参考例2（1.152 点）
- 既存シートとの一致（A社（サンプル） 0.48／36,458 円、B社（サンプル） 0.60／28,889 円）

## 要確認事項・実装メモ

- **仕様書とデータモデルが変わっています。** 仕様書 §3.3〜§4.1 は「1顧客＝1施設種別＋1周期、
  倍率は点検周期マスタが一律に持つ」前提でしたが、換算値算出フロー図に合わせて
  「設備区分 × 周期」で倍率が決まる形に作り替えました。設備は `customer_facilities` に分けて
  合算します。フロー図反映前の実装はタグ `v0.1-周期一律倍率` に残してあります。
- **点数の丸めを小数第3位までに変えています。** 仕様書 §4.1 は「小数第3位を四捨五入して
  第2位まで」でしたが、フロー図の参考例が 0.075 点・0.132 点・計 0.555 点と第3位まで
  扱っているため、第4位を四捨五入して第3位まで保持しています。表示は第3位に値があるときだけ
  3桁にします（0.48 はそのまま 0.48）。
- **点検スケジュールは事業場単位のままです。** 設備ごとに周期が違っても（需要設備2ヶ月＋
  太陽光6ヶ月など）、点検月は顧客の「訪問周期」から生成します。現場には事業場単位で行くためで、
  設備ごとに点検月を分けたい場合はスケジュール画面の作り直しが必要です。
- **蓄電所はフロー図に分岐の記載がありません。** 月1回（×1.0）だけを用意しています。
  実際の運用に合わせて設定 → 設備区分から周期を追加してください。
- **旧データの移行で設備区分を推定した箇所があります。** `npm run db:migrate` が旧スキーマを
  検出した場合、旧「施設種別＋容量」から設備区分を割り当てます。64kVA未満（小規模高圧設備か
  非常用予備発電設備ありか）と太陽光（自家消費か全量売電か）は判別できないため、
  実行時に「要確認」として一覧を出します。該当があれば顧客編集画面で設備区分を選び直してください。
- **請求月は請求サイクルから毎回導出しています。** 点検月（`customer_inspection_months`）と違って
  テーブルには保存していません。点検月のように月単位で手修正したい場合は、
  同じ形のテーブルを足す必要があります。
- **未入金の判定は「請求済みのもの」だけを対象にしています。** 請求チェックを付けていない過去月を
  未入金として赤く出すと、単に未処理なだけの月まで警告になってしまうためです。
  未請求の月は請求リストの「未請求のみ」フィルタで拾えます。
- **TypeScript は 6 系に固定しています。** Next.js 15 は TypeScript 7 のネイティブコンパイラに
  対応していません。TypeScript 7 を使う場合は Next.js 16.2.11 以降へ上げてください。
- **`npm audit` に transitive な指摘が出ます。** Next.js が抱える postcss / sharp、
  drizzle-kit が抱える esbuild のものです。`npm audit fix --force` は Next.js の
  ダウングレードを伴うため当てていません。LAN 内からのみアクセスする前提の運用です。
